# Token-Efficient Agent Workflows in Solarch Development

## 1. The Progressive Investigation Methodology

Large repository contexts and verbose CLI logs quickly flood an agent's context window, degrading reasoning quality and wasting tokens. To maintain efficiency without missing critical engineering facts, follow the 4-step progressive investigation workflow:

```text
Step 1: Compact Overview (rtk git status / rtk ls)
        ↓
Step 2: Identify Specific Errors (rtk tsc / rtk test / rtk lint)
        ↓
Step 3: Narrow File & Line Scope (rtk grep / rtk diff)
        ↓
Step 4: Request Full Context Where Required (rtk proxy / raw command)
```

### Investigation Lifecycle
1. **Compact Overview**: Obtain the macro repository state without loading full file listings or verbose status messages.
2. **Identify Failures**: Run build or test commands with failure-focused filters. Collapsing hundreds of passing test cases isolates the exact failed assertions.
3. **Narrow Scope**: Inspect only the modified hunks or relevant files rather than whole-repo diffs.
4. **Full Context on Demand**: Whenever an error message references an ambiguous trace, truncated output, or missing contextual lines, escalate immediately to raw commands or `rtk proxy`.

## 2. Realistic Token & Cost Arithmetic

Be precise about what command-filtering tools achieve. Avoid exaggerated claims about LLM bill reductions:

$$\text{Shell Output Reduction} \neq \text{Total LLM Token Reduction} \neq \text{Total Cost Reduction}$$

### Why Reductions Dilute:
1. **Context Window Composition**: Command output is only one component of input tokens. System instructions, project rules, conversation history, and user prompts constitute a large portion of the context.
2. **Input vs. Output Tokens**: Output tokens generated by the LLM are billed at significantly higher rates than input tokens on most frontier models.
3. **Estimation Methodology**: RTK estimates token counts as $\approx \frac{\text{bytes}}{4}$ without an embedded tokenizer. The reported reduction percentages (60%–90%) reliably measure shell byte compression, but absolute token counts and billing changes are approximations.

---

## 3. Tool Independence: RTK vs. Solarch

RTK is strictly an external developer CLI proxy. It must never be confused with Solarch components:

- ❌ **NOT** part of the Solarch runtime.
- ❌ **NOT** a dependency of `@solarch/core-client`.
- ❌ **NOT** required to run Solarch Server or platform SDKs.
- ❌ **NOT** an API modifier.
- ❌ **NOT** a blocker: if RTK is not installed on the developer's system, execute standard shell commands directly without raising errors or stalling progress.

---

## 4. Safety & Full-Fidelity Fallback Rules

**Engineering correctness strictly overrides token minimization.** Always transition to unfiltered output under the following conditions:

1. **Debugging Ambiguous Failures**: If a test fails with a truncated stack trace or an error line whose origin cannot be determined, immediately run `rtk proxy <test_cmd>` or the raw test command to inspect the complete trace.
2. **Critical Pre-Commit Review**: Before committing security-sensitive logic, database migrations, or core protocol changes, review the complete diff (`git diff`) rather than relying solely on condensed summaries.
3. **Contradictory Exit Codes**: If a command exits with code `1` but the filtered output appears empty or truncated, re-execute via `rtk proxy` to capture unhandled stderr.
4. **Interactive or Paged Commands**: Never pass interactive CLI prompts or paged logs through filtering proxies.
